# 只交付 Web 应用，桌面壳暂停

**Status**: accepted（取代 `0004-desktop-file-picking.md` 的前提）

## Context

v1 的交付形态包含一个 Tauri 桌面壳（`desktop/`）。它启动 sidecar 后把窗口 `navigate` 到 `http://127.0.0.1:<web_port>`，界面与浏览器版是同一份。这带来三件持续成本：

- 桌面壳的窗口跑在远程 http 源上，Tauri 不注入 IPC，任何需要系统能力的功能（文件选择、托盘、更新）都得先重构加载方式（见 ADR 0002 之后的探索与 ADR 0004）。
- 每次 UI 变更都要验证两种壳；桌面打包需要 Rust 工具链与三平台签名，而当前环境连 `cargo` 都没有。
- 产品要覆盖的两个场景里，场景 B（无图形界面的云主机）本来就只能开浏览器；场景 A（macOS 本机）开浏览器同样成立，因为代理与 UI 都在同一台机器上。

用户决定：桌面应用先不做，使用方式与 mitmweb 保持一致，只支持 Web 应用。目标用户已经熟悉 mitmweb 的心智模型，减少一套交付形态也减少一套文档与验证。

## Decision

Mitmboard 只以 **Web 应用** 交付：`mitmboard` 启动代理与 Web UI，用户用浏览器访问 `http://127.0.0.1:<web_port>`。仓库中的 `desktop/` 保留为历史代码，不构建、不发布、不承诺兼容；票 17（桌面改从 app 源加载并接原生文件选择）标记 `wontfix`。

## Considered Options

- **继续维护桌面壳**：多一套安装包与三平台签名流程，换来「双击图标」和系统文件选择；而系统文件选择可以用「手输路径」覆盖。
- **桌面壳改为从 app 源加载 UI**：技术上正确（IPC 同源、安全模型干净），但需要 Rust 工具链与打包验证，且与本轮「先与 mitmweb 对齐」的目标无关。
- **只交付 Web 应用**：最少维护面，与 mitmweb 的使用方式一致，两个目标场景都覆盖。

## Consequences

- README 不再宣称有原生桌面应用；桌面安装包不在发布物之列。
- Map Local 的文件字段在唯一形态下只有两种用法：上传进托管目录，或手输绝对路径（见 ADR 0004）。
- `desktop/` 目录的存在会让新读者误以为它是产品的一部分——由本 ADR 说明。
- 若将来恢复桌面端，必须先做「从 app 源加载 UI」的重构，再谈文件选择等系统能力。
