# 托管文件的生命周期：内容哈希命名、20 MB 上限、保存时清理加 TTL 保护

**Status**: accepted

Map Local 需要两类文件：浏览器上传的，和把已捕获响应存下来的。两类都写入托管目录 `~/.mitmboard/maplocal/`，以内容哈希加扩展名命名，相同内容只存一份。单文件上限 20 MB，约束上传与「存为文件」两条写入路径，超限返回 422 并提示改用手输路径。用户手输的、位于托管目录之外的路径永远不进入清理范围——那些文件不归我们管。

清理只在保存规则（整体 PUT）时执行：托管目录中不再被任何规则引用的文件被删除，但最近 10 分钟内写入的文件受 TTL 保护。TTL 是为了挡住两个真实场景：用户在对话框里上传后取消（文件暂时无引用），以及多个浏览器标签页各自持有不同的规则集同时保存（A 页的保存会按自己的规则集判断 B 页刚上传的文件无人引用）。

## Considered Options

- **上传即登记「待引用」集合，取消时显式回收**：语义最干净，但要引入一套跨请求的状态机与超时回收，且多标签页下仍需处理归属问题。
- **不做清理**：实现最省，但托管目录会随每次「存为文件」无限膨胀。
- **后台定期 GC**：与保存路径解耦，但需要一个常驻任务，且在没有请求时也会改动磁盘，排查问题时更难解释文件为何消失。

## Consequences

- 取消对话框留下的孤儿文件不会立刻消失，而是在下一次保存时被清理；这是刻意接受的延迟。
- 清理逻辑必须能区分「托管目录内」与「目录外」的路径，且不能信任客户端传来的路径字符串，需在服务端做前缀判定。
- 20 MB 是写入路径的约束，不是读取路径的约束：手输的超大文件仍会被正常读取并返回。
